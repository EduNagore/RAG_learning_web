## Objetivo

El **Model Context Protocol (MCP)** estandariza cómo una aplicación con un LLM (el *host*) se conecta a servicios que le ofrecen contexto y herramientas (los *servidores*). Por debajo es **JSON-RPC 2.0**: mensajes JSON con `method`, `params` e `id`. Vas a implementar el núcleo de un servidor: recibir una línea de texto con un mensaje, y devolver la respuesta correcta, incluidos los errores. Es lo que hay detrás de cualquier servidor MCP real, sin el transporte (stdio o HTTP), que solo mueve estas mismas líneas.

<Callout type="aviso" title="Qué revisión de MCP sigue este laboratorio">

El laboratorio sigue el esquema de las revisiones de la especificación **hasta la 2025-11-25**, que abrían la sesión con `initialize` y tenían `ping`. La revisión **2026-07-28** eliminó ese saludo y `ping`: cada petición lleva su versión y las capacidades del cliente en `_meta`, existe `server/discover` y los resultados incluyen un campo `resultType`. Lo que practicas aquí sigue vigente: JSON-RPC 2.0, `tools/list`, `tools/call` y la distinción entre errores de protocolo y errores de ejecución con `isError`. Si implementas un servidor real, sigue la especificación vigente y sus reglas de compatibilidad.

</Callout>

## Qué tienes que hacer

Completa `MCPServer.handle_line(line)`, que recibe **una línea de texto** y devuelve la respuesta como **texto JSON** (o `None` si era una notificación). El registro de herramientas (`add_tool`) ya está resuelto.

**Errores de protocolo** (la respuesta lleva `"error": {"code", "message"}`):

| Situación | Código | Mensaje | `id` |
| --- | --- | --- | --- |
| JSON inválido | -32700 | `Parse error` | `None` |
| No es un objeto, `jsonrpc` distinto de `"2.0"` o `method` que no es texto | -32600 | `Invalid Request` | el del mensaje si lo trae; si no, `None` |
| Método desconocido | -32601 | `Method not found: <método>` | el de la petición |
| `tools/call` con una herramienta que no existe | -32602 | `Unknown tool: <nombre>` | el de la petición |

**Métodos** (la respuesta lleva `"result"`):

- `initialize`: `{"protocolVersion": <el de params>, "capabilities": {"tools": {"listChanged": false}}, "serverInfo": {"name", "version"}}`.
- `ping`: `{}`.
- `tools/list`: `{"tools": [{"name", "description", "inputSchema"}, ...]}` en orden de registro.
- `tools/call`: con `params = {"name", "arguments"}`. Si va bien, `{"content": [{"type": "text", "text": str(valor)}], "isError": false}`. Si faltan argumentos obligatorios del esquema o la función lanza una excepción, **no es un error de protocolo**: se devuelve un resultado con `"isError": true` y el texto `falta el argumento obligatorio: <arg>` o `<Tipo>: <mensaje>`. Así el modelo puede leerlo y corregirse.

Una **notificación** es un mensaje válido **sin `id`** (por ejemplo, `notifications/initialized`): no se responde.

## Un ejemplo para comprobar a mano

```python
peticion = {"jsonrpc": "2.0", "id": 1, "method": "tools/call",
            "params": {"name": "sumar", "arguments": {"a": 2, "b": 3}}}
servidor.handle_line(json.dumps(peticion))
# '{"jsonrpc": "2.0", "id": 1, "result": {"content": [{"type": "text", "text": "5"}], "isError": false}}'
```

<Callout type="nota" title="Dos clases de error, dos destinatarios">

Un error de protocolo (método inexistente, petición mal formada) indica un fallo del **cliente** que el modelo difícilmente puede arreglar. Un error de ejecución de una herramienta (fecha en el pasado, recurso no encontrado) es información útil **para el modelo**: por eso viaja dentro de un resultado normal con `isError`. La especificación de MCP recomienda precisamente entregar estos últimos al modelo para que se autocorrija.

</Callout>
