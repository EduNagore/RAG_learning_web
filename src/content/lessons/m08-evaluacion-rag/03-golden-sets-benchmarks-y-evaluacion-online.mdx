## Intuición: sin un buen conjunto de pruebas, todo son opiniones

Cada decisión de un sistema RAG (tamaño de chunk, modelo de embeddings, reranker, prompt) mejora unas preguntas y puede empeorar otras. Sin un **conjunto dorado** (*golden set*), una colección de preguntas representativas con sus respuestas y documentos relevantes, las decisiones se toman por intuición o por la última demostración que gustó. Con él, cada cambio se acepta o se rechaza con números, y se detectan regresiones antes de llegar al usuario.

La evaluación tiene dos fases que se alimentan entre sí: **offline** (el conjunto dorado, antes de desplegar) y **online** (lo que ocurre con usuarios reales). Esta lección cubre cómo hacer bien ambas.

## Cómo funciona

### Qué debe tener un buen conjunto dorado

- **Preguntas reales.** Sácalas de tickets, búsquedas, chats con soporte y entrevistas con usuarios. Las preguntas que inventa el equipo suelen parecerse demasiado a los documentos y facilitan la recuperación.
- **Cobertura de tipos.** Un solo tipo de pregunta da una visión sesgada. Incluye al menos: un documento, varios documentos (de síntesis y de varios saltos), **sin respuesta**, con **restricciones de acceso** y casos difíciles (siglas, errores ortográficos, preguntas ambiguas).
- **Respuesta de referencia y evidencia.** Para cada pregunta: los documentos relevantes (para la recuperación) y una respuesta de referencia redactada (para la generación).
- **Etiquetado revisado.** Dos personas etiquetan una muestra y se mide su acuerdo; las discrepancias revelan ambigüedades en la pregunta o en los criterios.
- **Versionado.** El conjunto es parte del código: se guarda en el repositorio, con control de cambios, y cada resultado indica con qué versión se midió.
- **Conjunto de desarrollo y de reserva.** Usa una parte para ajustar y otra que **nadie toque** para validar.

### Auditar el conjunto y su tamaño

El código siguiente audita el conjunto dorado de Nimbus por tipos, calcula cuántas preguntas harían falta para un margen de ±5 puntos y compara BM25 con la fusión RRF **pregunta por pregunta** (diseño pareado) en lugar de solo mirar las medias.

```python
import math
from collections import Counter

import numpy as np
from ragkit.data import load_corpus, load_golden
from ragkit.embeddings import HashingEmbedder
from ragkit.text import tokenize

golden = load_golden()

# 1) Auditoría del conjunto dorado: ¿qué tipos de pregunta cubre?
tipos = Counter()
for q in golden:
    if not q["answerable"]:
        tipos["sin respuesta"] += 1
    elif len(q["relevant_ids"]) > 1:
        tipos["varios documentos"] += 1
    elif q["requires_access"] != "public":
        tipos[f"acceso {q['requires_access']}"] += 1
    else:
        tipos["un documento, público"] += 1
print(dict(tipos), "| total:", len(golden))


# 2) ¿Cuántas preguntas hacen falta para un margen de ±5 puntos?
def preguntas_necesarias(p, margen):
    return math.ceil(1.96**2 * p * (1 - p) / margen**2)


for p in (0.9, 0.5):
    print(f"p = {p}: {preguntas_necesarias(p, 0.05)} preguntas para ±5 puntos")

# 3) Comparación pareada de dos sistemas: ¿en cuántas preguntas gana cada uno?
corpus = load_corpus()
ids = [d["id"] for d in corpus]
docs = {d["id"]: tokenize(d["title"] + " " + d["text"]) for d in corpus}
avgdl = sum(map(len, docs.values())) / len(docs)
emb = HashingEmbedder()
E = emb.embed_many([d["title"] + ". " + d["text"] for d in corpus])


def bm25(query, k1=1.5, b=0.75):
    scores = {i: 0.0 for i in ids}
    for t in set(tokenize(query)):
        n = sum(t in d for d in docs.values())
        if n == 0:
            continue
        idf = math.log(1 + (len(docs) - n + 0.5) / (n + 0.5))
        for i, d in docs.items():
            f = d.count(t)
            if f:
                scores[i] += idf * f * (k1 + 1) / (f + k1 * (1 - b + b * len(d) / avgdl))
    return sorted(ids, key=lambda i: -scores[i])


def denso(query):
    return [ids[i] for i in np.argsort(-(E @ emb.embed(query)), kind="stable")]


def rrf(*rankings, k=60):
    puntos = {}
    for r in rankings:
        for pos, d in enumerate(r, start=1):
            puntos[d] = puntos.get(d, 0) + 1 / (k + pos)
    return sorted(puntos, key=lambda d: (-puntos[d], ids.index(d)))


def acierta(ranking, relevantes, k=3):
    return any(d in relevantes for d in ranking[:k])


gana_rrf, gana_bm25, empatan = [], [], 0
for q in golden:
    if not q["relevant_ids"]:
        continue
    rel = set(q["relevant_ids"])
    a = acierta(bm25(q["question"]), rel)
    b = acierta(rrf(bm25(q["question"]), denso(q["question"])), rel)
    if b and not a:
        gana_rrf.append(q["id"])
    elif a and not b:
        gana_bm25.append(q["id"])
    else:
        empatan += 1
print("solo RRF acierta:", gana_rrf, "| solo BM25 acierta:", gana_bm25, "| igual en", empatan)
```

Salida (determinista):

```text
{'un documento, público': 18, 'varios documentos': 3, 'acceso internal': 6, 'acceso restricted': 1, 'sin respuesta': 3} | total: 31
p = 0.9: 139 preguntas para ±5 puntos
p = 0.5: 385 preguntas para ±5 puntos
solo RRF acierta: ['q02'] | solo BM25 acierta: [] | igual en 27
```

- **La auditoría revela los huecos**: 18 de 31 preguntas son de «un documento público», solo 3 de varios documentos y 3 sin respuesta. El conjunto de Nimbus es suficiente para practicar, pero **insuficiente para decidir** sobre abstención o preguntas de síntesis.
- **El tamaño importa mucho:** para estimar una tasa de acierto en torno al 90 % con un margen de ±5 puntos hacen falta unas **139 preguntas**; con una tasa cercana al 50 %, **385**. Con 28 o 31 preguntas, el margen real es de unos ±11 puntos.
- **El diseño pareado cuenta lo que importa:** de 28 preguntas evaluables, RRF acierta una que BM25 no (`q02`), BM25 no acierta ninguna que RRF falle y en 27 empatan. La diferencia es **una sola pregunta**. Una prueba de signos con 1 contra 0 no da ninguna evidencia: sirve para describir el cambio («RRF rescató la pregunta del reembolso»), no para afirmar que RRF es mejor.

### Cómo crece un conjunto dorado en la práctica

Empezar con 150 preguntas perfectas es poco realista. Un camino que funciona en equipos pequeños:

1. **Semana 1: 30 a 50 preguntas** sacadas de tickets reales, con evidencia y respuesta. Es suficiente para detectar desastres, no para afinar.
2. **Cada incidencia suma una pregunta.** Cuando un usuario reporta una mala respuesta, el caso se añade al conjunto (anonimizado) con la respuesta correcta. Es la fuente más valiosa porque son los fallos reales.
3. **Cobertura por tipo antes que volumen.** Es preferible 10 preguntas sin respuesta bien elegidas que 100 más de «un documento público». Revisa la auditoría por tipos cada mes.
4. **Revisión periódica.** Los documentos cambian: una pregunta cuya respuesta cambió deja de ser válida y puede dar falsas regresiones. Asocia a cada pregunta la fecha y la versión del documento y revísalas cuando se actualice el corpus.
5. **Mide el acuerdo entre etiquetadores** en una muestra: si dos personas no coinciden en cuál es el documento relevante, la pregunta es ambigua y conviene reescribirla o quitarla.

### Preguntas sintéticas: útiles, pero con cuidado

Etiquetar a mano es caro, así que es común **generar preguntas con un LLM** a partir de los documentos (una pregunta por fragmento, con su respuesta). ARES (Saad-Falcon et al., 2023) usa generación de datos sintéticos para entrenar sus jueces y combina un conjunto pequeño de anotaciones humanas para corregir errores, y reporta que se puede evaluar con precisión con solo unos cientos de anotaciones humanas. Lo que conviene saber:

- **Las preguntas sintéticas son más fáciles que las reales:** comparten vocabulario con el fragmento del que salen, así que inflan los resultados de BM25 y de los embeddings.
- **Filtra** preguntas ambiguas, triviales o que no se pueden responder sin el contexto original («¿qué dice el segundo párrafo?»).
- **Mézclalas con preguntas reales**, y reserva las reales para decidir.
- **Cuidado con el juez y el generador iguales:** si el mismo modelo genera las preguntas y juzga, el sesgo se refuerza.

### Benchmarks públicos

Sirven para **preseleccionar** y para compararte con el mundo, no para decidir. **BEIR** (heterogéneo, *zero-shot*) y **MTEB** (8 tareas, 58 conjuntos, 112 idiomas, ningún método domina) miden recuperación y embeddings. **MultiHop-RAG** (Tang y Yang, 2024) es un benchmark de RAG con consultas de varios saltos sobre una base de noticias en inglés, con respuestas y evidencia de soporte, y sus resultados indican que los métodos de RAG existentes rinden de forma insatisfactoria en recuperar evidencia y responder esas consultas. Dos riesgos: **contaminación** (los modelos pueden haber visto los datos de evaluación en el entrenamiento) y **desajuste de dominio** (inglés y noticias, frente a tus políticas internas en español).

### Evaluación online

Con usuarios reales aparecen preguntas que ningún conjunto dorado anticipó. Las señales habituales:

- **Feedback explícito:** pulgar arriba o abajo y comentarios. Pocos usuarios lo dan y los que lo dan no son representativos.
- **Señales implícitas:** reformulaciones inmediatas, abandono, clics en las citas, escalado a una persona.
- **Evaluación automática sin referencia** (fidelidad, relevancia) sobre una **muestra** del tráfico, con LLM juez calibrado.
- **Revisión humana** de una muestra aleatoria y de los peores casos cada semana.
- **A/B y despliegues graduales:** envía la versión nueva a un pequeño porcentaje, compara métricas de negocio y de calidad, y revierte si empeora. Define **de antemano** la métrica principal y el tamaño de muestra, para no «encontrar» una mejora mirando 20 métricas.
- **Ciclo cerrado:** los fallos reales de producción pasan, anonimizados, al conjunto dorado. Así el conjunto crece donde el sistema flaquea.

Todo esto está sujeto a **privacidad**: las preguntas reales pueden contener datos personales; anonimiza y limita el acceso antes de guardarlas en el conjunto.

## Trade-offs

| Decisión | Ventaja | Inconveniente |
| --- | --- | --- |
| Conjunto pequeño y curado | Barato, de calidad | Margen de error grande; cobertura limitada |
| Conjunto grande sintético | Escala, barato | Preguntas más fáciles; sesgo del generador |
| Benchmarks públicos | Comparable, sin etiquetar | Contaminación; desajuste de dominio |
| Evaluación offline | Rápida, reproducible, previa al despliegue | No ve lo que no anticipaste |
| Evaluación online | Datos reales | Lenta, ruidosa y con privacidad |
| A/B en producción | Mide el efecto real | Necesita tráfico y definir métricas antes |

## Errores comunes en producción

- **Conjunto dorado sin preguntas sin respuesta ni permisos.** No mide abstención ni fugas de acceso.
- **Preguntas inventadas por el equipo.** Demasiado cercanas a los documentos: resultados optimistas.
- **Decidir con un conjunto de unas decenas de preguntas.** El margen es de ±10 puntos; «mejoras» de 3 puntos son ruido.
- **Ajustar sobre el conjunto de reserva.** Si lo usas para decidir, deja de ser independiente.
- **Mirar muchas métricas en el A/B y quedarse con la que sale bien.** Define la principal antes.
- **No versionar el conjunto.** No sabrás si una mejora viene del sistema o de que cambió el examen.
- **Fiarse de la contaminación de un benchmark.** Un buen resultado público puede deberse a datos vistos en el entrenamiento.
- **Guardar preguntas de usuarios sin anonimizar.** Es un riesgo de privacidad y legal.

<Callout type="entrevista" title="Preguntas típicas">

- _"¿Cómo construirías el conjunto de evaluación de un RAG?"_ Pista: preguntas reales, tipos variados (varios documentos, sin respuesta, permisos), evidencia y respuesta de referencia, etiquetado revisado, versionado y un conjunto reservado.
- _"¿Cuántas preguntas necesitas?"_ Pista: depende del margen; para ±5 puntos con una tasa del 90 %, unas 140; con muchas menos el ruido domina; usa diseños pareados e intervalos.
- _"¿Qué riesgos tienen las preguntas sintéticas?"_ Pista: son más fáciles, comparten vocabulario con el fragmento y refuerzan el sesgo del generador; mezclarlas con reales y filtrarlas.
- _"¿Cómo evalúas en producción?"_ Pista: feedback, señales implícitas, evaluación sin referencia sobre una muestra, revisión humana, A/B con métrica fijada de antemano y cierre del ciclo hacia el conjunto dorado.

</Callout>

<KeyTakeaways>

- Un **conjunto dorado versionado**, con preguntas reales, tipos variados y un subconjunto de reserva, convierte las opiniones en decisiones.
- **El tamaño importa:** unas 139 preguntas para ±5 puntos con una tasa del 90 %; con 28, el margen es de ±11.
- Compara sistemas **pregunta por pregunta**: en Nimbus, RRF frente a BM25 fue una pregunta de diferencia.
- Las preguntas **sintéticas** y los **benchmarks** públicos ayudan a escalar y preseleccionar, pero son más fáciles o menos representativos.
- La evaluación **online** (feedback, muestreo, A/B) alimenta el conjunto dorado: cierra el ciclo y cuida la privacidad.

</KeyTakeaways>
